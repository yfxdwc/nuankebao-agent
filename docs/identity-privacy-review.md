## §0 评审目的与适用范围

### 0.1 评审目的

D4 (主人 2026-09-25 拍) 把客户列表可见集合从「我的归属 + 我的直推加盟」两段式扩到「我的归属 + 下层加盟节点本人 + **下层归属的客户** + **上级推送的客户**」四段式,并引入 `customer_share` 表承载推送关系。本评审聚焦:

1. **隐私扩张点有哪些** — 哪些数据从「仅归属人可见」扩到「同枝下层 / 上级推送范围内可见」
2. **每一扩张点的缓解措施** — 集中收窄开关 / maskPhone / 限流 / 审计等
3. **残余风险与未决项** — 哪些需要主人**拍板**, 而不是 agent 自行决定

### 0.2 适用范围

| 在范围内 | 不在范围内 |
|---|---|
| 客户档案的手机号 / 姓名 / 健康字段在列表 / 详情 / 概览的可见性扩张 | 建号 / 落位 / 推荐码等**身份与关系**本身的口径 (主文档 §3 / ADR-0013 / ADR-0015) |
| `customer_share` 推送机制的越权 / 扩散 / 撤销时序 | AI 跟进话术 / 报表 (主文档 §0 「范围」明列排除) |
| 主文档 §8.4 Phase D 落地涉及的所有 API | 跨端类型代码改造 (主文档 §0 「范围」明列排除) |
| 销售员 (sales) 与店长 (manager) 两类角色 | 系统管理员 (`role='admin'`) — admin 全森林可见 (AGENTS §6.6.1 Q13) 不在扩围范围 |

## §2 隐私扩张点 (逐条 + 缓解)

> **编排原则**: 每条扩张点 = 「**扩张前 → 扩张后 → 隐私敏感度 → 缓解措施**」四列。每条至少一条「集中点」式缓解 (主文档 §3.4 「集中点」段)。

### 2.1 扩张点 E-A: 下级归属的客户对上级可见 (b2 子句)

| 字段 | 内容 |
|---|---|
| **扩张前** | 客户 X 的 `customer.owner_id = 下级 A`,则 X **仅 A 可见** |
| **扩张后** | A 的上级 B 也可见 X (B 的列表出现 X 行,归属 badge = 「下级的客户 · A」) |
| **隐私敏感度** | **中** — X 的手机号在 B 端**仍走 `maskPhone`** (主文档 §3.4 分级表 `subordinate` = mask);B 看到的是打码手机号 + X 的姓名 + 跟进历史摘要 |
| **缓解 (集中点)** | `customer-scope.ts::viewerCustomerScopeSql` 单一真相源 — 收窄 (b2) 子句为「仅直接下级」时**只动这一处** (主文档 §3.4 「集中点」段);调用方 (列表 / 详情 / 概览 / 计数 / 行级过滤) 零改动 |
| **缓解 (mask)** | 主文档 §3.3 B4 硬约束 + §3.4 分级表;`identity.ts::toView` 一处输出,所有 view 路径读这张表 |
| **缓解 (默认折叠)** | **待主人拍** — 列表行是否默认折叠 `(b2)` 类客户?需主人决定 (主文档 §4.2 表仅列了「L2 归属 badge 显形」,未明确默认折叠) |
| **缓解 (默认排序)** | **待主人拍** — `(b2)` 类是否排在 `(a)` 之后?`(c)` 是否再靠后?主文档未明确 |
| **缓解 (审计)** | `customer_share_audit` 触发器**不覆盖**此条 (此条非推送,而是结构性扩围);但 `customer` 表的现有 `customer_audit` 触发器**已覆盖** `owner_id` 的更新,可追溯「X 何时由 A 归属」 |

### 2.2 扩张点 E-B: 上级推送的客户对下级可见 (c 子句)

| 字段 | 内容 |
|---|---|
| **扩张前** | 客户 X 的 `customer.owner_id = 上级 C`,则 X **仅 C 可见**;C 没有显式授权机制让下级 D 看见 X |
| **扩张后** | C 主动推送给下级 D 后,D 也可见 X (D 的列表出现 X 行,归属 badge = 「上级推送 · C」) |
| **隐私敏感度** | **高** — X 的手机号在 D 端**明文** (主文档 §3.4 分级表 `upline_shared` = 明文,D8 2026-09-25 拍) |
| **缓解 (推送人限定)** | **S1**: 只有该客户的归属人 (`customer.owner_id`) **或** `role='admin'` 能推送 (主文档 §6.5.2 S1) |
| **缓解 (接收人范围)** | **S2**: 接收人必须是推送者所在枝的下层用户 (同 `root_id` + `placement_path` 前缀);admin 不受此限 (主文档 §6.5.2 S2) |
| **缓解 (跨枝防护)** | §3.4 (c) 子句「推送人必须与我在同一棵树」子查询 (reviewer P0-B);admin 无节点时豁免 |
| **缓解 (扩散上限)** | **S6**: 同一客户 active 推送数 ≤ 5;同一接收人每日收到 ≤ 100 (主文档 §6.5.2 S6) |
| **缓解 (禁止二次转发)** | **S7**: 被推送人不能把收到的客户再推给她的下层 (主文档 §6.5.2 S7) |
| **缓解 (推送幂等)** | **S4**: 同 `(customer, to_user)` 仅一条 active 推送 (部分唯一索引 `uniq_customer_share_active`);重复 → 409 `ALREADY_SHARED` |
| **缓解 (撤销即时性)** | **R-10 兜底** (主文档 §9.2 ★): `/api/customers` 不缓存可见集合;撤销响应立即触发客户端刷新;集成测试断言 100ms 内不可见;`idx_customer_share_to_active` 索引 `(to_user_id, revoked_at)` 保证撤销即过滤 |
| **缓解 (双方账号停用)** | **SHARE-4**: 推送双方账号任一停用 → 推送失效 (主文档 §6.5.6;§3.4 (c) 两个 `EXISTS user active` 子句对称) |
| **缓解 (审计)** | **SHARE-5**: `customer_share_audit` 触发器必挂;推送 / 撤销都留痕;事后能查「谁在什么时候把谁推给谁 / 什么时候撤销 / 撤销原因」 |
| **缓解 (撤销原因必填)** | `reason` 必填 (zod refine);进审计;防止「撤销不留痕」造成的责任真空 |

### 2.3 扩张点 E-C: 推送 = 明文手机号 (D8 主人拍)

| 字段 | 内容 |
|---|---|
| **扩张前** | 推送不存在,无明文手机号扩散场景 |
| **扩张后** | 上级推送的客户对接收人 **明文可见** (主文档 §3.4 D8 2026-09-25 拍) |
| **隐私敏感度** | **高** — 手机号在 §4 「敏感个人信息」边缘 (联系方式, 单独可识别自然人);扩散到接收人 = 主动授权,但**接收人一旦泄露 = 主数据失控** |
| **缓解 1: 推送授权必须有原因** | `note` ≤ 200 字 (zod refine);**必填**,用于事后追溯「为什么要推」 |
| **缓解 2: 接收人范围限定** | S2 同枝下层 (避免跨枝手机号扩散) |
| **缓解 3: 扩散上限** | S6: 同一客户 ≤ 5 个 active 推送 (避免一个人手机号扩散到 50 个下级) |
| **缓解 4: 禁止二次转发** | S7: 控制链稀释;避免「我的下级的下级的下级都能看到」 |
| **缓解 5: 撤销即时生效** | R-10 兜底 |
| **缓解 6: 双方账号停用失效** | SHARE-4 (降级 + 审计) |
| **缓解 7: 列表元数据 mask** | **`/api/customers/shares/received` 返回的列表元数据 (角标用) 手机号一律 `maskPhone`**;角标是元数据,不是客户档案 — 与 `upline_shared` 在档案详情页明文不冲突 (主文档 §9.3 Phase D 验收清单明列) |

### 2.4 扩张点 E-D: 图谱可见性 ≠ 列表可见性 (本 ADR §1.3 边界)

| 字段 | 内容 |
|---|---|
| **扩张前** | 图谱可见性 = 全树下层 + 上 3 层直系 (AGENTS §6.6.1 Q13, 2026-09-22 落);列表可见性 = 两段式 |
| **扩张后** | 列表可见性 = 四段式 (扩围);**图谱可见性不动** |
| **隐私敏感度** | **低** — 本条不引入新扩张,但显式归档以避免后人混淆 |
| **缓解 (边界显式)** | 本 ADR §1.3 表 + 主文档 §3.4 「集中点」段强调「(b2) 用 `root_id IS NOT DISTINCT FROM` 守卫」 |
| **缓解 (单一真相源)** | H1: 列表扩围只在 `customer-scope.ts` 一处;图谱在 `franchisee.ts::getPlacementTree` 一处;两者不共享口径 |

### 2.5 扩张点 E-E: 详情页手机号 (清单已扩,详情必须同步)

| 字段 | 内容 |
|---|---|
| **扩张前** | 详情页手机号可见性 = 列表两段式命中的行 |
| **扩张后** | 详情页手机号可见性 = 列表四段式命中的行 (主文档 §3.4 「集中点」段外推;§4.1.2 「隐性要求」) |
| **隐私敏感度** | **中** — 详情页有健康字段 / 跟进历史 / 备注等附加信息,扩围后下级能看到上级客户的完整跟进时间线 |
| **缓解 (详情单行过滤)** | `/api/customers/[id]` 接 `viewerCustomerScopeSql(viewer)` 单行过滤 (ADR-0019 §4.1.2) |
| **缓解 (健康字段再加密)** | 主文档 §5.2 + AGENTS §3「数据敏感字段必须加密」:健康字段 (健康状态 / 疾病史 / 养生记录摘要) 已走 `pgcrypto`;即使列表可见,健康字段**额外有字段级加密** |
| **缓解 (详情审计)** | `customer` 表的现有 `customer_audit` 触发器覆盖「读取」「更新」;事后能查「谁在什么时候看了 X 客户详情」(若系统记录读取) — **此项能力当前未启用,待主人拍** |

## §4 隐私合规自检清单 (PIPL §4 / §6 / §13 落地)

> **本节是项目内评审的「合规视角」对照**,不是法务意见。主人后续若引入第三方 DPO,需重新走完整流程。

| PIPL 条款 | 项目落地 | 出处 |
|---|---|---|
| **§4 (个人信息定义)** | 客户档案 (姓名 / 手机号 / 健康状态) = 个人信息;手机号 + 健康状态 = 「敏感个人信息」边缘 | 主文档 §1 + AGENTS §3「数据敏感字段必须加密」 |
