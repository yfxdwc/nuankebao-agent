# ADR-0016: 身份锚与同号识别 —— 邀请码是唯一识别码, 手机号只是联系方式

> **状态**: ✅ Accepted (2026-09-22 主人拍板)
> **日期**: 2026-09-22
> **影响范围**: `customer` · `user` · `franchisee` · `salon_guest` · 所有"同一个人"的连接判定 ·
> 建号 / 建档 / 落位流程 · 客户列表 UI · 账号生命周期
> **相关**: [ADR-0013 账号=客户](./0013-account-customer-binding.md) ·
> [ADR-0015 主体模型](./0015-subject-model.md) ·
> [ADR-0012 会员+推荐码](./0012-membership-billing.md) ·
> [ADR-0006 加盟边界](./0006-franchise-boundary.md) · AGENTS §6.6 / §6.6.1
>
> **本 ADR 修正 ADR-0015 §3 术语表的一处口径**: 自然人锚点从 `phone_hash` 改为**邀请码**。

---

## 1. 背景 (主人原话)

> 「**手机号不作为用户识别内容, 用户的唯一识别码是邀请码, 姓名可能有同名**; 但**手机号同号需要有识别提醒机制**。
> **谁约来的客人就是谁的客户或潜在客户, 但用户自决是否要应用内创建客户**。
> **生命周期要有初步机制, 留待后期完善**。
> **"她是 app 用户"还是"凭空建的客户", UI 上要有区别**。
> **"每个用户首先都肯定是另一个用户的客户" 这只是指现实中的, 应用内可能暂不映射现实**。」

**为什么要改 (现状的问题)**: ADR-0015 §3 把"一个自然人 = 一个 `phone_hash`"当作锚点, 于是全库用
`phone_hash` 相等来判定"同一个人" —— 但这有三个现实问题:
1. **手机号会换**: 改号后三面要靠同步脚本补, 漏一处就散架 (dev 实测 3 条节点漂移);
2. **手机号会共用**: 夫妻/父母子女共用一个号是真实场景, "同号 = 同人"会错误合并;
3. **姓名会重名**: 张伟/李娜这种名字本来就不唯一, 不能当识别。

而**邀请码**是系统发的、随机不重复、一人一码、终身不变 —— 它才是真正可靠的唯一识别码。

---

## 2. 决策

| # | 决策 | 落地含义 |
|---|---|---|
| **D1** | **唯一识别码 = 邀请码** (6 位, `referral_code`) | 需要"这是谁"时**首选邀请码**; 码终身不变、不能重发 |
| **D2** | **手机号 = 联系方式, 不做身份锚** | 保留在 `user/customer/franchisee` 三表, 但**不再**用于判定"同一个人" |
| **D3** | **姓名可重名** | 不做姓名唯一约束 / 不拿姓名匹配人 |
| **D4** | **系统内部连接一律走 ID**: `user.customer_id` (账号↔档案) + `user.franchisee_id` (账号↔节点) | 替换掉所有 `phone_hash = phone_hash` 的身份连接 (见 §3) |
| **D5** | **同号 → 识别提醒** (检测 + 提示 + 人工确认), **不静默合并** | 见 §4; 默认**不**允许同号两条档案 (待拍 fork) |
| **D6** | **沙龙客人归属带来人**; 是否应用内建档**由用户自决** | `salon_guest.brought_by_user_id` = 归属人; 提供「转为我的客户」入口 (Q6) |
| **D7** | **生命周期有初步机制** (停用/软删/退出图谱 三面口径 + admin 入口), 细节留待后期 | 见 §5 |
| **D8** | **UI 必须区分「已注册用户」与「凭空建档的客户」** | 客户列表/详情加 `hasAccount` 标记 |
| **D9** | **现实 ≠ 应用内**: 「每个用户首先是别人的客户」只描述现实, 应用内由用户显式添加 (Q12 不变) | 保持建号不自动归属 |

## 3. D3 落地清单: 把"身份连接"从 phone_hash 换成 ID

| 位置 | 旧 (phone_hash) | 新 (ID) |
|---|---|---|
| `customer-scope.ts` 直推加盟判定 | `franchisee.phone_hash = customer.phone_hash` | `customer.id = u.customer_id AND u.franchisee_id = franchisee.id` |
| 客户列表 `isMember` (会员标识) | `u.phone_hash = customer.phone_hash` | `u.customer_id = customer.id` |
| 「自己不应该是自己的客户」 | `customer.phone_hash <> 我的 phone_hash` | `customer.id <> u.customer_id` |
| 按码查人的 `self` 判定 | 比手机号 hash | 比 **user id** (`码主人 = 我`) |
| 沙龙快速邀请"她注册了吗" | `u.phone_hash = customer.phone_hash` | `u.customer_id = customer.id` |
| 落位/建节点"她必须有账号" | 按**手机号**找账号 | 🔄 后续改用**邀请码**找账号 (P6) |

> `phone_hash` 保留的正当用途只剩三类:
> ① **登录凭证** (user 侧, 手机号仍是最方便的登录名 —— 这是凭证, 不是身份);
> ② **同号提醒** (D5);
> ③ 历史数据迁移 / 兜底 (`user.customer_id` 为空的老行)。

---

## 4. D5 同号识别提醒机制 (要做的"提醒"长什么样)

**触发点**: 建档 / 建号 / 转客户时, 手机号与既有记录撞车。

**行为**: **不静默合并**, 而是停下来问人:

```
⚠️ 这个手机号已有记录
   · 客户档案: 张三 (已是 李四 的客户)
   · 账号: 已注册 (第 3 层加盟商)
   → [用这条已有档案 (加为我的客户)]  [不是同一个人]  [返回修改]
```

- 选「用已有档案」→ 走 `claim` (归属声明, 先到先得);
- 选「不是同一个人」→ **默认不允许**同号两条档案 (当前唯一索引) → 提示改用别的联系方式,
  或等 P5 拍板后放开;
- 所有"同号确认"进审计 (谁在什么时候把两个同号记录认成/没认成一个人)。

**待拍 fork (P5)**: 是否允许同一手机号存在**两条客户档案**?
- 允许 → 需要 `ADR-0004` 例外 (DROP UNIQUE INDEX `idx_customer_phone_hash`) + 登录侧
  (`user.phone_hash` 唯一) 与"同号提醒"的重写;
- 不允许 (默认) → 只提醒 + 引导用已有档案。

## 5. D7 生命周期初步机制 (先有骨架, 细节后期)

| 动作 | 含义 (三面口径) |
|---|---|
| **停用账号** (`user.is_active=false`) | 不能登录; **不删**客户档案、**不摘**加盟节点 (图谱里标"停用") |
| **软删客户档案** (`customer.deleted_at`) | 移出客户列表; 账号、节点不受影响 |
| **软删加盟节点** (`franchisee.deleted_at`) | 退出图谱/落位; 账号保留但视为"未加盟" |
| 联动 | **默认不级联** —— 危险动作要在 UI 里说清影响范围; 后期再评估级联规则 |

**初步机制** = ① 上表口径写进 AGENTS; ② 系统管理员可**停用/启用账号** (带 guardrail: 不能停用自己 /
不能停用最后一个 admin); ③ 每次停用写审计。
