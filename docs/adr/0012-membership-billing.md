## 1. 背景

暖客宝此前**没有任何计费能力** ("系统不收任何费用" 曾是 ADR-0006 里论证"不构成传销"的一句话)。
主人 2026-09-19 决定开始收费, 并给出产品口径:

- **个人订阅**: 每个用户自己充值 (不是门店/品牌代付)
- **免费档**: 除 9 项外的全部功能可用; **会员档**: 全部功能
- **价格**: ¥69/月 (单月) / ¥49·月 (开通自动续费)
- **到期**: 停止会员功能, **基础功能继续用**, 数据永不删
- **推荐码**: 每人固定 6 位; 注册可选填; 双方各得 15 天会员权益
- **收款**: 个体工商户账户; **收费与用户业务资金无关**

## 3. 红线 (与 ADR-0006 的关系)

ADR-0006 里"系统不收任何费用"这句话**必须随本 ADR 修订**为:

> 「加盟体系本身不收费; 软件订阅费与加盟资格 / 层级**完全解耦**。
>  App 会员收费与用户业务资金没有任何关系。」

三条不可破的约束 (任何 PR 违反 = 驳回):

1. **表隔离**: `billing_*` / `membership_*` / `referral_*` 表**不得**有外键指向 `franchisee` / `customer`;
   计费代码 (`src/lib/billing/**`) **不得 import** 加盟域查询 (`lib/db/queries/franchisee*`)。
   唯一允许的交叉: `membership.user_id → user.id`。
2. **计酬禁止**: 不出现现金返利 / 佣金 / 介绍费 / 团队计酬; 推荐奖励**只能是服务权益 (天数)**,
   不可提现、不可转让、不可折现; 无二级推荐。
3. **资格解耦**: 付费状态**不得**影响加盟身份、上下级关系、图谱位置、客户数据所有权。

### 3.1 系统管理员 = 永久会员 (主人 2026-09-19)

`role = 'admin'` 的账号**按规则**判定为永久会员 (`isMember=true`, `permanent=true`, `planCode='admin'`),
**不写任何权益行**。理由:

| 做法 | 问题 |
|---|---|
| ❌ 给每个 admin 发 3650 天权益 | 到期还得续; 换管理员要补数据; `entitlement_grant` 里一堆假流水污染审计 |
| ✅ 按 `role` 判定 (本 ADR) | 零数据零维护; 新管理员立刻生效; 降回 sales 立刻按真实权益算 |

**实现**: `getMembership()` 一次查询同时取 `user.role` + `membership` (leftJoin), `role='admin'` 直接返回
`{ isMember: true, permanent: true }`; `membershipSource: 'admin'`。`requireFeature` / `hasFeatureAccess` /
生日提醒过滤全部自动跟随 (它们都走 `getMembership`)。

**边界**:
- 只认 **数据库里的 `user.role`** —— 不信客户端、不信 session token 里能改的字段
- admin 仍然正常参与审计 (他做的每件事都记录), 只是不需要付费
- 员工/后台账号**不参与计费**: 不计入付费转化、不生成订单、推荐码照常可用 (不影响)
- 客户端表现: 「我的」页显示「管理员账号 · 永久会员 (无需付费, 不会到期)」, **不显示开通/续费入口**

## 4. 数据模型 (S0 落地)

```
plan                套餐 (free / monthly / monthly_auto) —— 价格版本化, 改价=新版本
membership          每用户一行; member_until = 权益截止 (会员判定的唯一真相)
entitlement_grant   送天数的流水 (推荐/赠送/补偿); idempotency_key 防重复
referral_code       每用户固定 6 位码 (去 0/O/1/I/L 易混字符)
referral_reward     推荐关系 + 发奖状态 (pending / rewarded / rejected)
order / payment / refund / webhook_event / billing_ledger   → S1 (支付) 才启用
```

**关键设计**:
- **不存冗余状态**: 会员与否由 `member_until > now()` 派生, 避免"状态字段与到期时间打架"
- **送天数不进钱账本**: `billing_ledger` 只记真实收付; 权益走 `entitlement_grant` (避免"权益=现金价值"联想)
- **幂等**: 发奖用 `idempotency_key` (如 `referral:12->34`), 重复触发不会重复送

## 5. 判权模型

- **服务端唯一安全边界**: `requireFeature(userId, key)` → 不是会员抛 `402 + code=MEMBERSHIP_REQUIRED`
- **客户端只做提示**: 从 `GET /api/me` 拿 `membership.features[]`, 隐藏/灰化入口; **不当作安全边界** (APK 可反编译)
- **免费功能零判断**: 基础功能不加判权, 避免误伤主流程
- **生日提醒的特殊处理**: 非会员读客户数据时 `birthdayRemindDays → null` (提醒自然不触发), **底层数据保留**,
  续费后原设置自动回来 (不删用户的设置)

9 个会员 feature key (`src/lib/billing/features.ts`):
`ai.assistant` / `ai.follow_up` / `ai.customer_profile` / `ai.effect_analysis` / `ai.repurchase` /
`meeting.salon` (未实施, 占位) / `crm.interaction` / `crm.birthday_reminder` / `media.upload`

> 例外 (实现口径): `POST /api/photos` 区分 `purpose` —— `wellness` (默认, 会员) 与 `avatar` (免费, 个人账号头像)。
> 理由: "图片上传"指的是**业务照片**; 个人头像属账号身份, 不该因未付费就不能换。

## 6. 推荐码机制 (★ 律师复核项)

| 项 | 规则 |
|---|---|
| 格式 | 6 位, 字符集 `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (无 0/O/1/I/L) |
| 归属 | 每用户 1 个, 注册即分配, 不可改 |
| 填写 | 注册时可选; **注册后不可补填** (防事后挂单) |
| 奖励 | 被推荐人 15 天 + 推荐人 15 天 |
| 触发 | 被推荐人: 注册+手机号验证后 (待确认口径); 推荐人: **被推荐人成为加盟者后** (D23) |
| 叠加 | 顺延 —— `member_until = max(now, member_until) + 15d` (不吞掉已付时间) |
| 上限 | 推荐人 月 30 / 累计 360 (D22, 可配) |
| 反作弊 | 一生一次 / 手机号 hash + 设备 + IP 去重 / 异常批量注册 → pending 待人工审 |
| 性质 | **服务权益**, 不可提现 / 转让 / 折现 / 开票; 与加盟资格、等级、价格**无关** |

**为什么仍要律师复核**: 双向送会员权益 = "推荐有奖", 落在《禁止传销条例》"拉人头"语义边缘。
五道护栏 (只送权益 / 仅一层 / 与层级无关 / 有封顶 / 协议写明) 是工程侧的最大努力, 不替代法律意见。

### 7.1 S0.5 人工收款通道 (主人 2026-09-19 拍: 内测用个人微信收款码)

**为什么**: 内测阶段没有商户号 (个体户/企业的微信支付进件要资质+审核), 但**会员功能要能卖**。
人工通道不依赖任何支付资质, 今天就能收钱。

**闭环 (全部在 App 内完成, 管理员不用开电脑)**:

```
用户: 我的 → 会员 → 开通会员 → 看到收款码 (金额 ¥69/月, ¥189/3月)
        → 微信扫码付款 → 回 App 填备注 (手机号后 4 位) ± 传付款截图 → 点「我已支付」
          (POST /api/billing/manual-payments, 状态 pending; 一人同时只能有一条)
管理员: 我的 → 管理员工具 → 付款申请(待审) → 核对到账 → 「通过并开通」
          (POST /api/billing/admin/manual-payments/[id], approve)
        → 立刻给该账号 +30 天 (grantDays, 幂等键 = 申请单 id)
用户:   我的 → 会员 → 会员中, 有效期至 X 月 X 日
```

**数据与接口**:
- 表: `billing_config` (key/value: 收款码 URL / 收款人 / 备注提示 / 开关) +
  `manual_payment_request` (申请单: 金额/天数/备注/截图/状态/核销人/实际给的天数)
- 用户: `GET /api/billing/pay-info`、`POST|GET /api/billing/manual-payments`
- 管理员: `GET /api/billing/admin/manual-payments?status=`、`POST .../[id]` (approve/reject)、
  `POST /api/billing/admin/pay-info` (换收款码, 不用改代码)
- 收款码来源优先级: `billing_config.manual_wechat_qr_url` (管理端上传到 `/uploads/`) >
  静态兜底 `public/payment/wechat-qr.png` (放文件即生效)

**边界 (硬)**:
- 金额只是"用户申报", **以管理员对账为准** (人工通道的本质); 驳回不产生任何权益
- 核销只有 `role=admin` 能调 (服务端每次查库, 不信客户端); 一条申请只能核销一次
- 一人同时只能有一条 pending (防刷屏); 核销写的天数记在申请单 + `entitlement_grant` 流水
- **付款截图上传必须免费** (`purpose=payment_proof`): 付钱的人还不是会员, 不能拿会员功能拦他
- 全部表挂审计触发器 (申请/核销/配置变更都留痕)

**已知限制 (内测可接受, S1 解决)**: ① 无自动续费 (人工通道做不到, 需用户手动) ② 到账核对靠人工
③ 无发票 ④ `¥49/月` 连续包月价在人工通道下不提供 (S1 在线支付上线后再给)

## 8. 后果

**正面**: 免费档让产品可无门槛试用; 会员档把有真实成本的 AI + 高价值 CRM 能力 (互动/生日/照片) 打包;
推荐码带来增长; 判权在服务端, 客户端不可绕过; 数据永不删 = 与"自托管"卖点一致。

**负面 / 代价**:
- 需要新的审计面 (`entitlement_grant` + 未来 `billing_ledger`) 与对账流程
- 推荐机制带来合规暴露面 (需律师复核 + 可收紧的封顶常量)
- 9 项判权散落在多个 route → 必须有"新增会员功能要挂 requireFeature"的 PR 检查项
