## 1. 背景

### 1.1 主人原话 (两轮)

**第一轮** (触发本 ADR):

> 「当前的客户体系和 app 用户体系还是有不够清晰明确的区分和关系。我们需要先**彻底理清楚这个底层**。」

**第二轮** (本版新增, 系统视角 + 用户视角的完整口径 —— 本 ADR 的权威产品描述):

> 「**系统视角**: 在 app 系统后台有全部用户数据, 用户分为**充值用户**和**免费用户**, 每个用户以随机分配的 **6 位推荐码**为**身份唯一性验证**, 用户名填用户的**真实姓名**; 用户与用户之前可能有关系, 通过**加盟图谱页**中用户之前发展出**树状图谱关系**; 图谱关系在系统数据库中同步体现, 在用户视角每个用户**只能看到自己所在的图谱树中自己所在的这一分支里低于自己层级的**加盟节点, 在**系统后台的数据图谱视角下 (系统管理员) 则能看到全部用户节点**, 有加盟的 (接入了某条加盟图谱树), 也有**孤儿节点** (未接入任何加盟图谱树)。
>
> **用户 (暖客宝 app 使用者) 视角**: 每个用户有自己的**客户列表**, 客户分为**加盟客户**和**未加盟客户**, 加盟客户就是用户**亲自开发出来的直推客户**, 未加盟客户可细分为**普通客户** (付费体验过养生服务) 和**种子客户** (未付费但已有基础资料信息的潜在用户), 用户的客户列表中的客户**可以是其他用户**也可以是**自己根据对方的基础信息凭空创建的客户**, 把其他用户添加到自己的客户列表有 **2 种方式**「1: 在提供推荐码推荐新用户注册成功后, 在用户的"**我推荐的人**"页面中可以看到被推荐者的卡片并可以在此把他**加为自己的客户**; 2: 在**新建客户时可填入对方的推荐码 (身份识别码) 快速新建客户**, 新建后可编辑以丰富基础信息」。
>
> **图谱是系统视角和用户视角共有的**, 不同的是系统视角能看到**所有用户的全图谱**, 用户视角**只能看到用户自己所在的加盟树的自己所在枝的下层全部节点以及自己的上层节点, 上层最多能往上看三层直系 (单线)**; 推荐码的主要作用是作为**用户身份唯一性识别**以及**推荐奖励会员资格的凭证**, **推荐码推荐关系不影响用户关系和加盟图谱关系**。」

### 1.2 触发起草的三次卡壳 (2026-09-22)

1. 修「自己不应该是自己的客户」: 发现**没有列**连接 `user` 和 `customer`, 只能靠手机号 hash 约定;
2. 修「列表「加盟」= 直推」: 发现「加盟」的判定散在 4 处, 且与测试注释写的口径已经不一致;
3. 想接 RBAC 行级过滤: 发现「**我的客户**」这个最基本的词, 代码里有 4 种互不相同的实现, 谁也说不清算哪个。

结论: 这不是某个查询写错了, 是**底层主体模型没有被定义过** —— 本 ADR 的目标是把它定义出来。

## 2. 产品模型 (主人口径 · 本 ADR 的权威描述)

### 2.1 系统视角 (管理员)

```
系统后台
├── 全部用户 (user)
│     ├── 充值用户 = 有会员权益 (membership.member_until > now; role=admin 永久)
│     └── 免费用户 = 已注册、无会员权益
│   每个用户:
│     ├── 用户名 = 真实姓名
│     ├── 登录标识 = 手机号 (唯一)
│     └── 推荐码 = 随机 6 位 (身份唯一性识别 + 推荐奖励凭证)
│
└── 加盟图谱 (全森林)
      ├── 已接入 = 挂在某棵加盟树的节点上
      └── 未接入 = 没有加盟节点的用户 (孤立在树外)
```

- 系统视角能看到**所有用户节点**: 已接入的 + 未接入的。
- 系统管理员能力 (§6.5 / §6.8): 建根 (`POST /api/admin/users/[id]/root`)、协商处理后强改上层 (`reparent`)。

### 2.2 用户视角 (app 使用者)

```
我的 (user)
├── 我的客户列表 (customer)
│     ├── 加盟客户     = 我亲自开发出来的直推客户 (结构: 挂在"我"下面)
│     └── 未加盟客户
│           ├── 普通客户 = 付费体验过养生服务
│           └── 种子客户 = 未付费、已有基础资料信息的潜在客户
│   客户可以:
│     ├── 是其他用户 (对方有账号, 已有客户档案)
│     └── 是我凭空创建的 (对方没有账号, 我录入姓名 + 手机号 + 资料)
│   把其他用户加为客户的两条路:
│     路 1: 推荐注册成功 → 「我推荐的人」页 → 把他加为我的客户
│     路 2: 新建客户时填对方的推荐码 (身份识别码) → 快速新建 → 再编辑丰富
│
└── 加盟图谱 (只读)
      ├── 向下: 我所在枝的**全部**下层节点 (不限层数)
      └── 向上: 最多 **3 层直系** (单线一条)
```

### 2.3 图谱可见性矩阵 (本次补充的核心)

| 对象 | 系统管理员 | 普通用户 | 现状代码 |
|---|---|---|---|
| 全部树 / 全部节点 | ✅ 全森林 | ❌ | `/api/admin/users` (Flutter「用户管理」页) |
| 未接入的用户 | ✅ | ❌ | 同上 (未加盟 计数) |
| 自己的树 | ✅ | ✅ | `/api/franchisees/me/tree` |
| 自己枝的下层 (不限层) | ✅ | ✅ | `getPlacementTree` (全子树; depth = 载荷旋钮) |
| 自己的上层 | ✅ | ✅ **最多 3 层直系** | ⚠ `getPlacementUpline` **只取 1 层** |
| 其他树 / 其他枝 | ✅ | ❌ | 列表过滤 (rbac.ts) 已按 path 子树 |

### 2.4 推荐码 (referral_code) 的职责

| # | 职责 | 落地 |
|---|---|---|
| 1 | **身份唯一性识别** (账号的 handle; 可用于"按码找人") | ☑ 已有码; ❌ **无查询接口** |
| 2 | **推荐奖励会员资格的凭证** (双向各 15 天; 月 30 / 累计 360 封顶) | ✅ `referral_reward` |
| 3 | **建号必填** (谁把我带进来的; ADR-0013; admin/根可空) | ✅ `createAccountWithProfile` |

**一条禁令** (主人明确): 推荐码的**推荐关系** ≠ 用户关系, ≠ 加盟图谱关系。
即: 用我的码注册的人, **不会**自动成为我的下级/下线; 只在"我推荐的人"里出现, 由我**显式**决定是否加为客户。

1. `/api/customers` 的 `listCustomers({...})` **没有 `rbacCtx`** → 每个销售员都能看到**全库客户** (CHARTER §3.6 红线明写禁止)。

   `session.user.role ?? 'sales'` 对**所有人**都判成 sales → 管理员 (dev id=7/8) 没有 `franchisee_id` 时**加盟列表直接返回空**。

## 5. 决策清单 (✅ 已拍板 2026-09-22)

> ✅ **拍板记录**: 2026-09-22 主人回复「**全按建议**」—— 下列 Q1–Q16 **全部按每条给出的「建议」选项通过**
> (含最核心的归属模型: 新增 `customer.owner_id` · 建档 ≠ 归属 · 建号不自动归属推荐人)。
> 下文保留选项与代价作为决策依据; **「建议」= 已生效的决策**, 实施顺序见 §7。
>
> 分组: **A 身份与推荐码** / **B 图谱** / **C 客户归属 (最核心)** / **D 关系边** / **E 边界与存量**

### A. 身份与推荐码

#### Q1 (v1) 「客户」是一类还是两类?

- 选项 A (**建议**): 不拆表。`customer` = **主体档案**, 有/无账号只是它的两个状态, 用**派生标记** `has_account` (由 `phone_hash join user` 得出) 区分。
- 选项 B: `customer.kind = 'account' | 'walk_in'` 落列 (需回填 + 兼容)。
- 选项 C: 拆 `customer` + `lead` 两张表。
- **建议 A 的理由**: 拆表牵动健康数据 / 跟进 / 图谱 / 沙龙 / RBAC 全链路, 收益不抵风险; `has_account` 是纯派生, 不引入新真相源。

#### Q7 (v1) 加 `user.customer_id` (additive)

- 选项 A (**建议**): 加可空列 + 回填 + 唯一约束。从此账号↔档案**有列可查**; 同时**合并两条建号实现** (`signup.ts` → `registration.ts`)。
- 选项 B: 继续用 `phone_hash` 约定 (现状)。
- **代价**: 一次 additive migration + 回填脚本 (配 `pnpm db:compat`)。

#### Q10 (新) 推荐码规格 + 身份查询接口

- 规格: **建议保持 6 位字母数字** (现状)。32^6 ≈ **10.7 亿**, 碰撞概率可忽略;
  ⚠ 若改**纯 6 位数字** = 100 万空间: 1000 用户时至少一次碰撞概率 **≈ 39%** (`onConflictDoNothing` 重试能兜住生成, 但 **1M 空间极易被枚举** —— 一旦开放"按码查人", 枚举代价太高)。
- 查询接口: **建议新增** `GET /api/referral/lookup?code=XXXXXX` (登录可用), 返回 **姓名 + 打码手机号 + 会员标识**;
  **不返回**完整手机号 / 健康字段; 必须**限流 + 审计** (防遍历)。
- 落点: `src/lib/billing/referral.ts` (已有 `normalizeReferralCode` / `isValidReferralCodeShape` 可复用)。

### B. 图谱可见性

#### Q13 (新) 用户向上 3 层直系

- 选项 A (**建议**): 实现 —— 新增 `getPlacementAncestors(fid, 3)` (按 `placement_path` 去尾即得祖先链), 图谱与列表过滤同口径。
- 选项 B: 维持 1 层 (现状)。
- **代价**: 小 (一条查询 + Flutter 图谱画 3 格)。

#### Q14 (新) 消歧: 「直推」与「孤儿」

- **「直推」读哪栏** —— 主人本轮说「加盟客户 = 我亲自开发出来的直推客户」。
  字面可读 `referrer_id` (谁拉的) 或 `placement_parent_id` (挂谁下面)。
  2026-09-22 已拍「列表加盟 = 直推 = **点位父**」, 且本轮明确「推荐关系不影响用户关系和加盟图谱关系」→ **建议确认: 直推 = `placement_parent_id`**。
- **「孤儿节点」一词二义** —— 建议统一为:
  - 主人口径 → 文档/UI 说「**未接入**」(= 没有加盟节点, `user.franchisee_id IS NULL`); 避免与 §6.7 混。
  - §6.7 口径 → 一律说「**无账号节点**」(禁止存在, 见 `audit-orphan-nodes.ts`)。

### C. 客户归属 (本 ADR 最核心的一组)

#### Q11 (新) 归属 vs 建档 —— 是不是同一件事?

- 背景: 现在 `customer.created_by` 一列**干两份活** (谁建的档案 + 她在谁的客户列表)。
  主人模型里"加为我的客户"是**显式动作** → 需要能表达"这条档案我加了, 但不是我建的"。
- 选项 A: 维持 `created_by` 单列 (建档人=归属人), 不加列。
- 选项 B (**建议**): **加 `customer.owner_id`** (可空, additive, 回填 = `created_by`), 语义 = **归属人**;
  `created_by` 退回"建档人"(审计)。"我的客户"读 `owner_id`。
- 选项 C: 多归属链接表 (`customer_owner`: 一条档案可被多人添加)。
- **建议 B 的理由**: 主人两条添加路径都是"加**已存在**的档案"(对方已是用户 ⇒ 档案已存在),
  单列 `created_by` 表达不了; B 是最小 additive 改动; C 等真有"一个客户多个销售"需求再说。
- ⚠ **前置理解 (需要主人确认)**: 选了 B 就有一个**空档期** —— 新注册用户的档案最早是"无归属"的,
  要等推荐人/任何人**显式添加**才进某个列表。

#### Q12 (新) 建号时是否自动把归属给推荐人?

- 现状: **自动** (`signup.ts` 把 `createdBy` = 推荐人; 且写 `customer.referrer_id` = 推荐人档案)。
- 主人口径: 「在"我推荐的人"页面…**可以在此把他加为自己的客户**」→ 是**显式**动作。
- 选项 A (**建议**): **不自动**。建号只建档 (§6.6 不变量), 归属留空; 推荐人在「我推荐的人」页一键添加 (先到先得)。
- 选项 B: 维持自动 (那"加为我的客户"按钮退化为确认状态)。
- **代价 (A)**: 产品语义变化 —— 新注册用户在被添加前**不属于任何人的客户列表**;
  需一条一次性**存量策略** (`scripts/backfill-account-customer-link.ts` 可扩展)。

#### Q2 (v1) 「我的客户」= ?

- 选项 A: `created_by = 我` (W5 现成写法)。
- 选项 B (**建议**): **归属我的人 (`owner_id = 我`) ∪ 我的直推加盟 (点位父 = 我)** —— 与 2026-09-22「列表加盟 = 直推」自然衔接。
- 选项 C: `customer.referrer_id = 我的档案` (老带新口径, 与主人"推荐关系不影响"冲突)。
- ⚠ **阻塞前置**: 要接行级过滤, 必须**先补 `session.role`** (现在 JWT 没有 role → 会把 admin 也当 sales 过滤)。
  顺序: **先 session.role → 再 Q2**。

#### Q15 (新) 重复添加 / 冲突规则

- 场景: 用推荐码添加的人, 已有归属 (别人的客户)。
- 建议: **先到先得** —— 已有归属 → 明确报错「该手机号已是 XX 的客户」; 不做抢单; 多归属留待 Q11-C 评估。
- 同手机号去重: 沿用 `customer.phone_hash` 唯一 (一个自然人一条档案, §6.6)。

### D. 关系边纪律

#### Q3 (v1) 一条边只管一类问题 (禁止交叉)

| 问题 | 唯一真相源 |
|---|---|
| 谁把我带进 app (发会员天数 / 推荐奖励) | `referral_reward` (边 1) |
| 我挂在谁下面 (图谱 / 落位 / 上下级可见性) | `franchisee.placement_parent_id` (边 3) |
| 谁把我拉进加盟 (业务展示, **不参与任何判定**) | `franchisee.referrer_id` (边 2, 只读展示) |
| 客户"老带新" | 见 Q4 |

- **建议采纳**。规则: 任何权限 / 可见性 / 计数 / 奖励判定, **只允许引用上表最后一列**;
  其余边只能展示, 且必须在代码注释里标「仅展示」。

#### Q4 (v1) `customer.referrer_id` 死链路

- 选项 A (**建议**): **废弃** —— 删 `/api/customers/graph` + `myCustomerGraphProvider` + `CustomerGraphView`;
  `POST /api/customers` 与 Flutter 表单去掉「选择推荐人」; `signup.ts` 停写。
  列**保留** (ADR-0004 禁止 DROP), 标 `@deprecated 仅存量`。
- 选项 B: 接一个 UI 出口 (客户图谱 tab 展示老带新)。
- **建议 A 的理由**: 没有产品需求在用; 与主人「推荐关系不影响用户关系」一致; 留着只会继续误导 (本 ADR 起草时自己就踩过)。

### E. 边界与存量

#### Q5 (v1) admin / 根账号要不要客户档案?

- **建议**: `role='admin'` **显式豁免**建档; 根加盟商 / 普通 sales **必须**有同手机号档案 (ADR-0013 D1 不变)。
- 理由: prod 实测 admin (id=1) 无档案; admin 不是任何人的下线。
- 落点: `registration.ts` + AGENTS §6.6 + `scripts/smoke-registration.ts` 覆盖豁免分支。

#### Q6 (v1) 沙龙带约客人算不算客户?

- **建议**: **不自动建档** (避免中老年销售看到大量"只来过一次"的名单), 提供「**转为我的客户**」一键入口。
- 落点: `modules/salon/*` + `salon_guest` → `customer` (新功能, 单独排期)。

#### Q8 (上一轮追加) `store` / `staff` / `store_staff` 怎么办?

- 现状: **0 行**, 但 RBAC 的"同店"分支靠它。
- **建议**: **冻结**。「我的客户」不带门店维度; CHARTER §3.6 的「必须有 store_id 过滤」红线改成「必须有**归属**过滤」。
  多店台账 = Phase 3 的事。

#### Q9 (上一轮追加) 一个人的"消失"没有统一语义

- 现状: `user.is_active` (停用) / `customer.deleted_at` (软删) / `franchisee.deleted_at` (软删) **互不联动**。
- **建议**: 先用本 ADR §3 写死三面的生命周期口径 (停用账号 = 不能登录但不删档; 软删档案 = 移出客户列表; 软删节点 = 退出图谱),
  **实现**留到有真实离职/删除需求时再单开。

#### Q16 (新) 存量修复

- 清单: dev 254 条孤儿推荐码 / 3 个无账号节点 / 36 个无档案账号; prod admin 无档案。
- **建议**: 拍板后写一个**幂等巡检+修复脚本** (`scripts/audit-subject-integrity.ts`: `--check` / `--fix`), 形态参考 `audit-orphan-nodes.ts`。
- ⚠ dev 的 `customer` 表**已清空** (0 行) —— 修复前先确认 dev 数据是否可重建 (seed)。

## 6. 目标模型 (✅ 已定)

### 6.1 一页图

```
                    一个自然人
              identity = phone_hash (加密手机号, 唯一锚点)
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   ┌────▼────┐      ┌─────▼─────┐     ┌─────▼──────┐
   │ 账号面   │      │  客户面    │     │  结构面     │
   │ user    │      │ customer  │     │ franchisee │
   ├─────────┤      ├───────────┤     ├────────────┤
   │ 能登录   │      │ 被谁维护   │     │ 挂谁下面    │
   │ 充值/免费 │      │ 健康档案   │     │ placement_ │
   │ 推荐码   │      │ 归属人(*)  │     │ parent_id  │
   └────┬────┘      └─────┬─────┘     └─────┬──────┘
        │                 │                 │
        └──────── 真连接 (拍 Q7 后) ─────────┘
             user.customer_id   → customer.id     (Q7 新增)
             user.franchisee_id → franchisee.id   (既有)

   推荐码 (referral_code) ── 身份识别 + 奖励凭证; 不表达任何关系
   关系边 (Q3):
     账号推荐  referral_reward            = 唯一真相 (发奖)
     点位结构  franchisee.placement_parent_id = 唯一真相 (图谱/可见性)
     加盟推荐  franchisee.referrer_id     = 仅展示
     客户老带新 customer.referrer_id      = 废弃 (Q4)

   客户列表 (Q2) = 归属我的人 (owner_id=我, Q11 新增) ∪ 我的直推加盟 (点位父=我)
   客户分类       = 加盟 (直推) / 普通 / 种子(人工勾选)
```

### 6.2 三条不变量 (✅ 已写进 AGENTS §6.6)

1. **一个自然人 = 一个 `phone_hash`**; 账号面 / 客户面 / 结构面**都是它的可选面**, 不是三个独立的人。
2. **有账号 ⇒ 有客户面** (ADR-0013, admin 豁免 Q5); **有节点 ⇒ 有账号** (§6.7)。
   两面都由**唯一建号入口**创建 (Q7 合并), 并有**列**可查 (`user.customer_id`)。
3. **任何"谁的谁"的判定, 只允许读 Q3 表里的那一列**; 其余是展示字段 (推荐码 ≠ 关系)。
