# ADR-0013: 账号 = 客户 (建号即强制建档) + 推荐码必填

> **状态**: ✅ Accepted (主人 2026-09-19 拍板)
> **日期**: 2026-09-19
> **影响范围**: 建号路径 (`createAccountWithProfile`) · 账号档案不变量 · 推荐码归属 · 存量补齐
> **相关**: [ADR-0012 会员 + 推荐码](./0012-membership-billing.md) (推荐码规则来源) ·
> [ADR-0006 加盟边界](./0006-franchise-boundary.md) (红线) · AGENTS §6.7

---

## 1. 背景 (主人提问 + 实测)

主人问: 「用户网络和加盟网络是打通的吗。每个用户首先都肯定是另一个用户的客户」

查真实数据后发现**一半打通、关键一半没打通**:

| 关系 | 状态 |
|---|---|
| 加盟商 → 客户档案 (同手机号) | ✅ 32/32 (落位时自动建档) |
| 客户类型「加盟」= 派生 (不存字段) | ✅ 已实现 |
| 加盟商推荐人 (`referrer_id`) | ✅ 31/32 (根为空, 正确) |
| **账号 → 客户档案** | ❌ **0/7** (只靠"手机号 hash 相同"这个**约定**, 没有强制, 也没有 FK) |
| 推荐码 = 账号身份标识 | ⚠️ 只有 2/7 账号有码 (ADR-0012 说"注册即分配", 实际未落实) |
| 推荐码 → 客户图谱 | ❌ 不写 `customer.referrer_id` (两套推荐概念各走一条) |
| 无推荐人的客户 | ❌ 38/47 (导入存量) |

即「每个用户首先都肯定是另一个用户的客户」这条**当时不成立**: 账号可以从"石头里蹦出来"
(如新建管理员), 在系统里不属于任何人。

## 2. 决策 (主人拍板)

| # | 决策 | 内容 |
|---|---|---|
| D1 | 建号即强制建档 | 任何建号路径 → **必须有同手机号的 customer 档案** (已存在则复用, 不重复建) |
| D2 | 推荐码必填 | 非 admin/根账号, 建号时**必须**填推荐人的 6 位推荐码 (谁把我带进来的) |
| D3 | 推荐码 = 最强身份识别码 | 每账号 1 个、注册即分配、不可改; 它是账号关系的锚点 (账号层推荐关系) |
| D4 | **no_link** | 推荐码**不写** `customer.referrer_id` —— 会员/账号推荐关系 ≠ 客户图谱老带新, 两条线各自独立 |
| D5 | 存量补齐 | 账号补档案 (+补推荐码); 无推荐人的客户**挂到门店/根** |

## 3. 落地 (提交实现)

- **唯一建号入口** `src/lib/auth/registration.ts::createAccountWithProfile()`
  - 校验: 姓名 / 手机号 / 密码策略 / **推荐码必填** (admin 或 `allowNoReferral` 可空)
  - 事务内 (`withAuditContext`): 建 user + 建/复用 customer 档案
  - 事务外: `ensureReferralCode()` (自己的码) + `claimReferralCode()` (推荐人奖励, ADR-0012 §6)
  - 附带 `ensureAccountProfile()`: 给**已存在**账号补档案 + 补码 (幂等; admin 脚本/存量补齐共用)
- `scripts/import-users.ts` (邀请制批量建号) 改走该入口; CSV `referral_code` 从"选填"变**必填** (admin 行可空);
  逃生舱 `--allow-missing-referral` (建根账号/首批种子账号用, 会打印警告)
- `scripts/ensure-admin.ts` (管理员账号长期保留) 顺带补齐档案 + 推荐码
- `scripts/backfill-account-customer-link.ts` 存量补齐 (幂等, 支持 `--dry-run`)
- `scripts/smoke-registration.ts` 冒烟: 无码被拒 / 建档成功 / 码归属 / no_link / 重复号 409 / admin 豁免

**实测结果** (2026-09-19 补齐后): 账号 7/7 有客户档案、7/7 有推荐码; 无推荐人客户 0 (44 个挂到根 #47)。

## 4. 不变量 (以后所有建号都必须满足)

1. 每个 `user` 有且只有一条 `customer` 档案 (同手机号)
2. 每个非 admin 账号都有推荐人 (通过推荐码; 根/管理员可空)
3. 每个账号有自己的推荐码 (不可改)
4. `customer.referrer_id` **不受**推荐码影响 (D4)
5. 所有写操作走 `withAuditContext` (audit_log)

## 5. 后果 / 已知缺口

- ✅ 「每个用户首先都是别人的客户」从**约定**变成**强制** (建号路径唯一 + 冒烟守住)
- ⚠️ **用户 ↔ 客户仍是手机号 hash 约定, 无 FK 列** —— 本次不引入 `user.customer_id`
  (避免与并行迁移编号冲突; 且现有约定 + 建号强制已足够)。后续若要更硬: 加 `user.customer_id` (additive, 可空)
  并在 DB 层加唯一约束。
- ⚠️ 存量补齐把 44 个无推荐人客户**统一挂到根** (= 门店直客)。若日后要按"加盟推荐人"细分,
  可再跑一次更精细的映射 (留 replace 口子)。
- ⚠️ 客户图谱 UI 目前**不显示**账号推荐链 (D4 的结果); 想看图请用「会员/推荐」视角 (ADR-0012 域)。

## 6. 候选评估

| 方案 | 结论 |
|---|---|
| **A. 建号强制建档 + 推荐码必填** (选中) | 改动集中在一个入口; 约定变约束; 不动 DB schema |
| B. 只在加盟/邀请入口强制 | 改动最小, 但登录后自建账号仍可能是孤岛 → 不满足主人"肯定"二字 |
| C. customer 为唯一业务主体 (彻底统一) | 最干净但牵动登录/权限/加盟/图谱, 风险大; 留作后续 (见 §5) |
| D. 推荐码同时写 `customer.referrer_id` | 主人明确 no_link (D4): 账号推荐 ≠ 客户图谱老带新 |
