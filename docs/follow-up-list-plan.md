## §0 一句话方案

**服务端算一个「跟进紧急度」分数 + 一条「推荐标签」，客户列表按紧急度分组排序，名字右边显示标签，
顶部给「今天要联系 N 位」的提醒条；点进去有该客户的跟进分析（频次/间隔/趋势 + AI 解读）。**

## §1 目标与边界

| 目标 | 说明 |
|---|---|
| **今天该联系谁** | 打开客户列表 3 秒内知道：先打给谁（新客 vs 老客 vs 要掉的） |
| **为什么是他** | 标签/理由必须能一句话说清（21 天没联系 / 生日 2 天后 / 复购窗口到了） |
| **提醒不漏** | 站内可见（列表顶部 + 我的页角标）→ 后续本地通知 |
| **可解释** | 排序理由服务端算、客户端只展示（单一真相，不搞两套算法） |

**明确不做**（对齐项目 vibe / 反模式）：
- ❌ 销售漏斗 / 转化率看板 / 冷冰冰的数字大屏
- ❌ 复杂图表（雷达图/热力图）；只用曲线 + 数字 + 一句话
- ❌ 让用户自己配置权重（中老年用户不配权重；规则由产品定）
- ❌ 打卡式强推（不做「未完成扣分」；只呈现轻重缓急）

## §3 核心：跟进紧急度模型（服务端计算）

### 3.1 输入信号（全部来自已有数据，不加用户负担）

| # | 信号 | 数据来源 | 触发条件 | 分值 | 档位 |
|---|---|---|---|---|---|
| S1 | **跟进任务逾期** | `follow_up_task` pending & `due_at < now` | 逾期 | `40 + min(20, 逾期天数×2)` | 免费 |
| S2 | 跟进任务今天到期 | 同上 | `due_at` 在今天 | 30 | 免费 |
| S3 | **距上次联系** | `interaction` 最近一条 | 4-7 天 8 / 8-14 天 18 / 15-30 天 30 / 31-60 天 42 / >60 天 55 | 分档 | 免费 |
| S4 | **从未联系（新客）** | `interaction` 空 | 建档 > 3 天且 0 联系 | 35 | 免费 |
| S5 | 养生记录断档 | `wellness_record` 间隔 | 历史平均间隔 × 2 未到店 | 25 | 免费 |
| S6 | 超长期未到店 | 同上 | > 90 天未到店 | +10（封顶 100） | 免费 |
| S7 | **生日窗口** | `customer.birth_*` + `birthday_remind_days` | 落在提醒窗口内 / 当天 +60 | 45 / 60 | **会员** |
| S8 | **复购窗口到** | `lib/ai/predictions.ts` | 预测复购日已到 | 50 | **会员** |
| S9 | 类型加权 | `customer_type` | 加盟商 +5 / 种子 +5 | 5 | 免费 |

> **分档取最大，不叠加**（S1 与 S2 互斥；S3 只取一档）；总分 `min(100, Σ)`。
> **免费档**：S7/S8 不参与 → 分数天然低一档，但**排序仍然可用**（不会因为没买会员就乱序）。

### 3.2 分级（决定列表分组与颜色）

| 级别 | 分数 | 文案（用户看到的） | 颜色 |
|---|---|---|---|
| **P0** | ≥ 80 | 🔴 今天必须联系 | `#D3545C` (danger) |
| **P1** | 60-79 | 🟠 本周联系 | `#E89F4D` (accent) |
| **P2** | 40-59 | 🟡 两周内联系 | 暖黄 `#D9B23D` |
| **P3** | 20-39 | 🟢 正常节奏 | `#4A7C59` (primary) |
| **P4** | < 20 | ⚪ 休眠池 | 灰 `#9AA5A0` |

### 3.3 可解释性（必须在 UI 上给理由）

服务端返回 `reason`（取分数最高的 2 个信号拼一句话）：

- `跟进任务逾期 3 天 · 已 21 天没联系`
- `生日 2 天后 · 上次电话是 40 天前`
- `新客户还没联系过 · 建档 9 天`

**规则**：宁可理由少而准，不要堆一长串；**永远不用"算法建议"这种黑话**。

## §4 推荐标签（客户名右侧）

### 4.1 标签清单（按优先级取 **1 个**，日历/生日类可与紧急标签共存最多 2 个）

| 优先级 | key | 标签 | 触发 | 档位 |
|---|---|---|---|---|
| 1 | `overdue` | 🔥 该回访了 | S1 逾期 | 免费 |
| 2 | `birthday` | 🎂 生日 3 天 | S7 窗口内 | 会员 |
| 3 | `repurchase` | 🔁 复购窗口 | S8 已到窗口 | 会员 |
| 4 | `new_lead` | 🌟 新客首访 | S4 | 免费 |
| 5 | `cold` | ⚠️ 掉线 30 天 | S3 31-60 天档 | 免费 |
| 6 | `stale` | 💤 沉睡 60 天 | S3 > 60 天 | 免费 |
| — | （无） | 不显示 | 正常节奏 | — |

**原则**：正常客户**不给标签**（安静），让"要动手的"跳出来；标签 ≤ 4 个汉字，字号 ≥ 13sp。

### 4.2 视觉规范（对齐现有 `FranchiseChip` / 生日徽章）

- 形状：圆角胶囊，底色 = 主题色 12% 透明，文字 = 主题色，高 22-24pt
- 位置：紧跟客户名右侧（`Row` 内 `Flexible` 名字 + `SizedBox(8)` + 标签）
- 交互：**点击标签** = 直接打开对应动作（该回访了 → 记一次互动；生日 → 生日卡；复购 → 养生记录）
- 现有 🎂 生日徽章**并入本体系**（不再单独一套），避免名字右边堆两个胶囊

## §5 提醒体系（三层）

| 层 | 位置 | 内容 | 期次 |
|---|---|---|---|
| **L1 列表顶部** | 客户列表 sticky 条 | `🔴 今天要联系 3 位 · 已逾期 1 位 → 展开` | P0 |
| **L2 待办页** | 「我的」→ 跟进待办（新页 `/follow-ups`） | 今日 / 本周 / 逾期 三组 + 一键"记一次互动"完成 | P1 |
| **L3 本地通知** | Flutter `flutter_local_notifications`（无需服务端/无需 FCM） | 每日 08:30 一条：「今天有 3 位客户要跟进」→ 点击进 L2 | P2 |
| （后续） | 服务端推送 | 多设备/离线推送；国内需厂商通道，暂缓 | P3 |

**任务自动生成**（避免"提醒只存在界面里"）：
- 系统每日 07:00 跑 `scripts/refresh-follow-up-tasks.ts`（复用现有 systemd timer 机制）
- 规则：生日窗口首日 → 建任务；复购窗口开启 → 建任务（会员）；S3 进入 P0/P1 → 建「该联系了」任务
- **幂等**：同客户同原因 7 天内只建一条；已存在 pending 同类任务 → 不重复建

## §6 排序与分组

### 6.1 排序规则（第一规则 = 紧急度，如主人拍板）

```
1. 紧急度分档 (P0 → P4)          ← 第一规则
2. 分数降序                      ← 同档内：更急的在前
3. 距上次联系天数降序            ← 再同分：越久没联系越前
4. 建档时间升序 (老客户优先)      ← 最后兜底，保证稳定
```

### 6.2 用户可切换的排序（顶部胶囊，默认「紧急」）

| 选项 | 规则 | 说明 |
|---|---|---|
| **紧急**（默认） | 上面 6.1 | 主人拍板的第一规则 |
| 最近联系 | `last_interaction_at DESC` | 刚聊过的在上 |
| 最近添加 | `created_at DESC` | 现状行为（老用户习惯兜底） |
| 姓名 | 拼音/汉字 `name ASC` | 找特定人 |

> 排序偏好本地持久化（`shared_preferences`，同现有设置页做法）；**筛选胶囊（全部/加盟/普通/种子）保留不变**。

### 6.3 分组展现（仅在「紧急」排序下）

```
🔴 今天必须联系 (3)
   [客户行...]
🟠 本周联系 (5)
🟡 两周内 (8)
🟢 正常节奏 (21)
⚪ 休眠池 (12)   ← 默认折叠
```
分组头吸顶 + 可折叠；分页保持 `limit/offset`（分组在**当前页内**成组，跨页由 `summary` 汇总）。

## §7 跟进分析

### 7.1 客户维度（详情页新增「跟进分析」卡，位于 AI 区之前）

| 指标 | 计算 | 展示 |
|---|---|---|
| 近 30 / 90 天联系次数 | `interaction` count | `近30天 3 次 · 近90天 7 次` |
| 平均联系间隔 | 相邻互动天数中位数 | `平均 12 天联系一次` |
| 趋势 | 最近 3 次间隔 vs 历史中位数 | `变冷了（21 → 9 天）` / `在变热` |
| 到店规律 | `wellness_record` 间隔 | `每 14 天到店 · 最近 09-14` |
| 复购间隔 | 历史到店/复购的中位数 | `复购间隔中位数 28 天` |
| 未完成跟进任务 | `follow_up_task` pending | `1 条待办（逾期 3 天）` |

### 7.2 列表维度（列表顶部摘要条）

`今天要联系 3 · 逾期 1 · 本周 5 · 休眠 12`（点击可跳到对应分组）

### 7.3 AI 解读（**会员**，复用 `lib/ai/follow-up.ts`）

- 输入：上面的客观指标 + 客户画像（不传健康明细原文，走现有 prompt 层脱敏口径）
- 输出：一句话建议 + 一句开场话术（已有能力，直接接）
- 非会员：展示客观指标 + 「升级会员看 AI 解读」（不锁数据）

## §8 数据模型与迁移（全部 additive，守住 ADR-0004）

```sql
-- 0015_follow_up_columns.sql (additive, 无破坏性)
ALTER TABLE customer ADD COLUMN last_interaction_at timestamptz;   -- 冗余: 最近一次互动
ALTER TABLE customer ADD COLUMN last_visit_at       timestamptz;   -- 冗余: 最近一次到店(养生记录)
CREATE INDEX idx_customer_last_interaction ON customer (last_interaction_at NULLS FIRST);
CREATE INDEX idx_customer_last_visit       ON customer (last_visit_at);
-- down.sql: DROP INDEX + DROP COLUMN
```

- **为什么冗余**：排序/分页必须在 SQL 层做（不能拉全表到内存算），
  计算 `MIN/MAX(interaction.created_at)` 的子查询在大表上会拖垮分页。
- **维护点**（写路径统一更新，避免漂移）：
  - `POST /api/interactions` → 更新 `last_interaction_at = greatest(现值, 新值)`
  - `POST /api/wellness-records` → 更新 `last_visit_at`
- **回填**：`scripts/backfill-last-contact.ts`（幂等；从 interaction / wellness 全量回填）
- **紧急度不落库**：随查询计算（`CASE WHEN` 表达式 + 索引），仅在 P3 真遇到性能问题时才升级成物化列

## §9 API 契约（`GET /api/customers`）

### 9.1 请求

| 参数 | 值 | 默认 |
|---|---|---|
| `sort` | `urgency` \| `recent` \| `new` \| `name` | `urgency` |
| `group` | `1` = 返回分组信息 | `0` |
| 既有 | `search` / `type` / `limit` / `offset` | 不变 |

## §13 风险与对策

| 风险 | 对策 |
|---|---|
| **性能**（万级客户算紧急度） | 冗余列 + 索引 + `LIMIT` 分页；P0 上线后压测 5k 行；不行再上物化列（列已预留） |
| **隐私**（AI 拿健康数据） | 走既有 prompt 脱敏层；AI 字段仅会员返回；不落第三方日志（MiniMax 国内 endpoint） |
| **噪音**（老花眼看不清） | 每行最多 1 个标签；标签 ≤4 字；颜色 + 文字双编码 |
| **判权漏洞**（前端藏了后端没拦） | 所有会员字段在 route 首行判权（沿用 ADR-0012 口径），漏判 = 白送 |
| **排序口径漂移** | 紧急度只在服务端算一处（`lib/follow-up/urgency.ts` 纯函数 + 单测）；客户端不算分 |
| **提醒变骚扰** | 每日通知仅一条（08:30 汇总）；不做"每分钟催" |
| **老客户端** | `followUp` 是**新增键**（老 APK 忽略即可）；`sort` 不传=新默认（可显式传 `new` 回退） |
